# FamilyCradle implementation decisions

These decisions resolve ambiguities found during the Phase 1 BRD review. The BRD remains the source of product requirements.

| Topic                 | Decision                                                                                                                                                                                                                                                    |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Multi-child log IDs   | The client-supplied UUIDv7 is the base ID and identifies the first child entry. Sibling entries use deterministic UUIDv5 IDs derived from the base ID and child ID. This is an explicit exception to the UUIDv7 convention and supports idempotent retries. |
| Optional vaccines     | Persist a `follow_optional` flag on each child-vaccine row, defaulting to false. Optional endemic vaccines count as late only after a parent opts in.                                                                                                       |
| Vaccine status        | `given_date` is authoritative for `done`; `status_override` is only `skipped`. Marking done clears `skipped`, and marking skipped clears `given_date`.                                                                                                      |
| Audit retention       | Active-family audit rows are retained for up to one year. Family deletion purges its audit rows with the rest of the family data after the seven-day restore window.                                                                                        |
| Authentication schema | Better Auth core tables are generated by its CLI and managed by Drizzle migrations. Custom account-consent fields are additive; Better Auth core columns remain untouched.                                                                                  |
| Authentication limits | Better Auth database-backed limits cover global traffic and sign-up. Atomic Drizzle counters enforce sign-in limits per IP/email pair and password-reset limits per normalized email; stored keys are SHA-256 digests and expire after 24 hours.            |
| Breached passwords    | Use Better Auth's Have I Been Pwned plugin. It checks a password using only the first five characters of its SHA-1 hash; the full password is never sent to the service.                                                                                    |
| Logging availability  | Logging is online-only. The PWA may cache its static shell, but failed edits are reported and are not stored for later replay.                                                                                                                              |

## Deferred before deletion flows ship

- Account deletion must preserve the required "Mantan anggota / Former member" attribution without retaining unnecessary personal data. Decide the exact anonymized representation before implementing account deletion in Phase 1.6.
- Medical and reference seed values marked `[VERIFY]` must be checked by a qualified reviewer before public launch; this document does not validate those values.
